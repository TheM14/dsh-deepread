# dsh-deepread 1.1.0

This release updates the optional Web client for DeepSeek Harness `0.2.0-rc.2` (the desktop runtime). The Node `deepread` tool, packaged skill, dsh-TUI Community Consensus `v0.15` manifest, and all data formats are unchanged from `1.0.1`.

## What changed

- **Current-session resolution migrated.** Harness `0.2.0-rc.2` removed the `current` field from the `sessions.list` snapshot. The panel's submit channel now reads the live binding from the `uiSession` service (`ctx.uiSession.adapter.current`, whose `.value.key` is the session id) and addresses the composer directly by id through `ctx.conversation.input.shell(sessionId)` instead of `input.for(sessionScope)`.
- **Browser activation conditions extended.** The client bundle's `exports.inject` and `package.json#dsh.client.inject` now also name `uiSession` / `@deepseek-ai/dsh-client-ui-session`. Host dev dependencies moved from `0.1.2-rc.1` to `0.2.0-rc.2`.
- **Real-host tests migrated to the published runtime layout.** The version gate now validates `0.2.0-rc.2` and resolves the real `ClientModuleSystem` from the shipped `@deepseek-ai/dsh-client-modules` bundle (queue facade + parsed boot manifest) instead of monorepo `packages/client/...` sources. The real-DOM drag test mounts the plugin components with react-dom + jsdom from dev dependencies, so it no longer requires an upstream source checkout. Theme tokens are cross-checked against the shipped `dsh-client-ui-theme` runtime bundle.
- **Compatibility guidance.** On Harness `0.1.2-rc.1` keep DeepRead `1.0.1` (its Web client predates the `uiSession` service); on the older `0.1.0-rc.7` Web runtime keep DeepRead `1.0.0`.

## Entry points and hosts

- Node Host entry stays `lib/types/index.js` (strict TypeScript, built by `tsc`); the dsh-TUI Host-only manifest stays `dsh-plugin.json` (Community Consensus `v0.15`).
- The same tarball keeps serving DeepSeek Harness Web (loads `lib/client.js`), Harness headless, and dsh-TUI (Host tool + skill only, no browser UI).
- Node.js `^22.19 || >=24` remains the engine requirement.

## Data and rollback

- No data migration or conversion: the URL cache domain, calibration storage, and browser localStorage keys are byte-identical to `1.0.1`.
- Rollback to `1.0.1` (or the `0.5.4` legacy procedure) follows [../upgrade-and-rollback.md](../upgrade-and-rollback.md) unchanged.
